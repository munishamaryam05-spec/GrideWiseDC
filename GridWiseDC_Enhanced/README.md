# GridWise DC — Enhanced 3D Digital Twin

A hardware-connected digital-twin demo for joint optimisation of AI data-centre resources. This package preserves the project scope in the project plan: ESP32 temperature sensing and physical LED/fan/buzzer actuation, MQTT messaging, a multi-rack digital twin with independent per-rack temperatures, cooling/water/grid/battery scenarios, explainable rule-based decisions, and illustrative baseline-vs-optimiser comparisons.

## Project structure

- `dashboard/index.html` — single-file browser dashboard with interactive Three.js 3D rack view, animated fans/airflow/water particles, temperature chart, scenario controls, browser-generated alarm sound, simulation mode, and HiveMQ WebSocket MQTT option.
- `esp32/gridwise_esp32.ino` — ESP32 firmware for DHT22, three LEDs, fan driver, active buzzer, and HiveMQ MQTT.
- `README.md` — setup and safety notes.

## 1. Run the dashboard

1. Extract the ZIP.
2. Open `dashboard/index.html` in a current version of Chrome or Edge. An internet connection is required for the CDN-hosted Three.js, MQTT.js, Tailwind CSS, and Chart.js libraries.
3. It starts in **Simulation** mode; no hardware or broker is required to explore the 3D racks and scenarios.
4. Click **Sound: off** once to enable browser audio. Browsers require a user gesture before playing sound. The software alarm sounds when the simulated or received telemetry reports the buzzer as ON.
5. Use the scenario buttons to demonstrate AI surge, heatwave/grid peak, drought, cooling failure, and renewable surplus. Drag to orbit the 3D view and scroll to zoom.

## 2. Hardware and wiring

Default firmware pins:

| Component | ESP32 GPIO |
|---|---:|
| DHT22 data | 4 |
| Green LED (with suitable resistor) | 25 |
| Yellow LED (with suitable resistor) | 26 |
| Red LED (with suitable resistor) | 27 |
| Fan driver/MOSFET input | 14 |
| Active buzzer module | 32 |

Use a common ground where appropriate. **Never connect a DC fan directly to an ESP32 GPIO.** Use a suitable MOSFET/driver or relay module and a suitable external fan supply; include flyback protection for inductive loads where required. Check your specific buzzer module's voltage/current requirements. Change the pin definitions if your wiring differs.

## 3. Upload ESP32 firmware

1. Install Arduino IDE and ESP32 board support.
2. Install these libraries through Library Manager: **PubSubClient**, **ArduinoJson**, and **DHT sensor library** by Adafruit (plus **Adafruit Unified Sensor**).
3. Open `esp32/gridwise_esp32.ino`.
4. Replace `YOUR_WIFI_NAME`, `YOUR_WIFI_PASSWORD`, and the HiveMQ host/user/password placeholders.
5. Create/configure a HiveMQ Cloud cluster and MQTT credentials. The ESP32 uses TLS port **8883**.
6. Select the correct ESP32 board and serial port, then upload.
7. Open Serial Monitor at **115200 baud** to see connection status and telemetry.

The firmware's `secureClient.setInsecure()` is included for quick demo setup and does not validate the broker certificate. Do not use this shortcut in a production deployment; install and validate the appropriate CA certificate.

## 4. Connect the browser dashboard to HiveMQ

1. Ensure the browser has network access and the broker permits WebSocket TLS connections.
2. In the dashboard click **MQTT settings**.
3. Enter the HiveMQ cluster hostname only (no `https://`), WebSocket TLS port **8884**, username, and password; click **Connect to MQTT**.
4. The dashboard subscribes to `gridwise/rack1/telemetry`, `gridwise/facility/state`, and `gridwise/optimizer/decision`. The ESP32 publishes `gridwise/rack1/telemetry` and subscribes to `gridwise/rack1/command`.
5. The dashboard sends fan/LED/buzzer commands to `gridwise/rack1/command`. The ESP32's local temperature safety rules may override dashboard commands at the next sensor cycle.

If MQTT fails, verify the cluster hostname, credentials, TLS ports, broker ACLs, and internet access. Do not share credentials or commit real passwords to a public repository.

## 5. What is real vs simulated?

- **Real hardware telemetry**: rack 1 temperature, fan state, LED state, and physical buzzer state received over MQTT.
- **Per-rack temperatures**: in Simulation mode, all six racks have independently drifting temperatures, individual °C labels, temperature-based LED colours, and fan animation. In ESP32 live mode, Rack 1 uses the physical sensor and the other five rack temperatures are offset estimates for visual demonstration until additional sensors are installed.
- **Browser alarm**: a sound generated by the dashboard when telemetry says `buzzer: true`; it is separate from the physical ESP32 buzzer. Enable it with the sound button first.
- **Optimiser and comparison metrics**: rule-based illustrative demo logic, not a validated industrial controller or measured energy/water savings.

The water loop is represented visually in the digital twin. This firmware does not control a real water pump or measure water flow.

## 6. MQTT message format

Telemetry example:
```json
{"temperature":32.4,"fan":"LOW","led":"YELLOW","buzzer":false,"rack":"rack1"}
```
Command example:
```json
{"fan":"HIGH","led":"RED","buzzer":true}
```

Topics:
- `gridwise/rack1/telemetry`
- `gridwise/rack1/command`
- `gridwise/facility/scenario`
- `gridwise/facility/state`
- `gridwise/optimizer/decision`

## Demo flow

1. Start in Normal operation and show the 3D racks.
2. Enable browser sound.
3. Trigger **AI training surge**, then **Heatwave + grid peak**.
4. Trigger **Water restriction** and show the cooling-water loop is visually paused.
5. Trigger **Cooling failure** and show red status, high fan, and alarm behavior.
6. Show the optimiser explanations and baseline-vs-GridWise illustrative indices.
7. If hardware is available, connect MQTT and demonstrate live temperature/fan/LED/buzzer state.

## Limitations / next steps

This is a demonstration digital twin. It does not yet implement a mathematical optimiser, predictive control, reinforcement learning, real water-flow instrumentation, multi-rack physical sensors, or a production-grade security model. The visualisation and example decision rules are intended to demonstrate the project concept and trade-offs described in the project plan.
